Changes from 68be7c6 to HEAD
================================

Purpose
-------
This document describes the changes introduced between commit 68be7c6 and the
current HEAD (1576a1b5). It is intended as a porting guide for applying the
same behavior to a divergent develop branch. Treat the change as one
coordinated refactor: the combat API moves, settings migration, consumers,
and settings UI depend on one another.

Range summary
-------------
- 42 paths changed.
- 1,733 lines added and 552 removed.
- Main themes: consolidate combat functionality under module/combat, migrate
  legacy combat settings, add a custom settings application, and redirect all
  consumers to the new API.

Recommended port order
----------------------
1. Add the combat module types, public index, and moved implementations.
2. Register the new combat settings and add the generic legacy-setting
   migration helper.
3. Wire combat migration into startup and preserve the GM-only execution
   behavior.
4. Update every consumer import and API call, including actor, chat, effects,
   token, canvas, modifier-bucket, and combat-tracker code.
5. Add the custom settings application, template, styles, and localization.
6. Update declarations, TypeScript configuration, tests, and changelog.
7. Remove obsolete files only after all imports have been redirected.

Settings and migration
----------------------
Combat settings are registered with config=false and exposed through a
dedicated CombatSettingsApplication. The settings accessors should be read
through the combat module API instead of reaching into the old registration
module.

Legacy setting keys retain their values but gain the combat namespace segment:

  Old key                                  New key
  ---------------------------------------  -----------------------------------
  use-on-target                            combat.use-on-target
  maneuver-visibility                      combat.maneuver-visibility
  maneuver-detail                          combat.maneuver-detail
  maneuver-updates-move                    combat.maneuver-updates-move
  allow-roll-based-on-maneuver             combat.allow-roll-based-on-maneuver
  initiative-formula                       combat.initiative-formula
  rangeStrategy                             combat.rangeStrategy
  use-size-modifier-difference-in-melee    combat.use-size-modifier-difference-in-melee

The old keys are stored under the existing GURPS namespace, so the migration
maps GURPS.<old key> to GURPS.<new key>. Values are currently passed through
unchanged. Keep the exact spelling and case of rangeStrategy; it is part of
the persisted setting key.

module/migration/settings-migration.ts provides the reusable migration
engine. Its required behavior is:
- inspect world settings under a namespace prefix;
- match only explicitly configured oldName entries;
- support synchronous and asynchronous value transforms;
- save all transformed values before deleting renamed legacy entries;
- use Promise.allSettled so one failure does not prevent other migrations;
- delete only successful migrations whose key changed;
- preserve failed legacy entries so a later launch can retry;
- allow in-place migrations without deleting their setting;
- notify when a migrated setting requires reload.

module/combat/migrate.ts builds the eight mappings above and invokes the
helper only for the GM. Startup wiring in module/gurps.js must invoke the
combat migration/setup path and must no longer initialize the removed
miscellaneous-settings module.

Porting cautions
----------------
- Do not port only module/combat in isolation; consumers still depend on the
  old paths until their imports and calls are updated.
- Preserve migration ordering and exact persisted keys. Partial migrations
  can create both old and new settings, and rerunning a migration can delete
  old entries after successful writes.
- Reconcile Foundry compatibility declarations and initialization hooks with
  the develop branch before removing old files.
- Resolve conflicts in module/gurps.js, module/combat/index.ts, actor/token/
  integrations, localization, and tsconfig.json first; those are the most
  likely divergent surfaces.
- Keep the migration failure policy: failed entries must not be deleted.
